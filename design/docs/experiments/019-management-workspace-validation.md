## 结论

**实验结论：成功，但存在性能问题。**

Angular 固定外壳、`.mgo` 动态业务界面、独立绘制桥和 Go 管理 MRPC 的主要接入链路已验证可行。性能问题集中在含标准库依赖的浏览器源码编译路径，不阻塞本实验的前后端方案可行性结论；浏览器直接编译仍按已验证范围使用。此总体结论不改变下文各子项的实际通过、失败和主动取消记录。性能修复进展见[工作台接入状态](../research-plan.md#management-extension)。

主链路最终 14 项检查全部通过；另一个采用宿主工具链预编译镜像的补充实验通过了类型化视图绘制、受控 TypeScript RPC 桥接、界面替换及显式草稿保留四项检查。两种调用方式均实际到达 Go 服务：界面直接使用生成的 Mini-Go RPC 客户端，以及界面经受控桥调用生成的 TypeScript 客户端。

浏览器 `/tools` 可以分析、查询和编译本实验的小型纯逻辑工作区。原发布包对包含生成 RPC 绑定与视图序列化依赖的完整工作区，在 `open` 阶段触发 `step_limit`；精简为类型化视图和 `ffi` 调用后，仍触发 `compiler request deadline`。随后保持两份输入和编译器镜像不变，在独立实验构建中进行[预算追加对照](#compiler-budgets)：同时增加步数与期限后出现分配超限；再扩大逻辑堆／对象额度、关闭累计步数限制并延长至 300 秒，两份工作区仍未完成 `open`。**默认预算是直接停止原因，但本次放宽没有解决浏览器编译；不能据此承诺只调整默认值即可使用。**原失败与各次对照分别保留。

[后续诊断](#compiler-diagnosis)未发现原调用方式错误，确认小型 FFI 引用会带入较大的标准库依赖，并采样到 VM 执行、GC 和计时开销。

因此继续采用现有前后端分工：正常展示加载匹配的编译镜像；源码编辑可由宿主编译并返回诊断和镜像；浏览器本地编译只对支持范围内的工作区开放。完整浏览器编译能力需要后续库改进或针对实际界面依赖重新核对，不作为管理工作台运行的必要条件。

## 实验结构与判定方式

Angular 创建固定外壳和业务挂载区。`.mgo` 返回带稳定标识的视图，独立 TypeScript 绘制桥更新限定区域内的标题、文本、输入框、按钮和文件控件。真实点击、输入和页面状态作为检查入口；固定读取、停止与可信测试机密输入独立于界面 VM。

一份 `.mrpc` 声明生成 Go Provider、TypeScript 客户端和 Mini-Go 客户端。Go 夹具维护修订、字段、操作和原请求回执，并在 Gateway 绑定会话身份和执行域，逐次校验角色、领域和业务前提。状态观察采用快照及可取消的有限等待。故障注入端点只用于断开真实连接和读取测试状态，不是拟交付接口。

| 路径 | 计算与调用链 | 用途 |
| --- | --- | --- |
| 主链路 | Go 原生编译 → MRPC 返回镜像 → 浏览器 WASM 执行界面 → 生成的 Mini-Go 客户端 → Go Provider | 验证直接 RPC、页面交互、状态观察、控制和故障处理 |
| 默认桥接补充 | Go 工具链预编译 → 浏览器 WASM 返回类型化视图／发起 FFI → 受控 TypeScript Provider → 生成的 TypeScript 客户端 → Go Provider | 验证设计中的受控管理桥，无需在界面内导入完整 RPC／JSON 辅助库 |
| 浏览器语言工具 | npm `/tools` → `open`／`analyze`／查询／`prepare` → 浏览器执行镜像 | 分别检查小型工作区成功范围与实际界面工作区的限制 |

独立浏览器会话核对宿主状态，断线用例在宿主接受修改后切断连接，再以原请求标识查询；没有用重发成功代替原操作核对。主链路的页面事件、宿主结果、请求记录、控制台、截图及 Playwright trace 随运行保存。

## 浏览器编译预算追加对照

追加实验检验原失败是否仅由默认预算造成。使用原失败的完整工作区与精简 `ffi` 工作区，源码字节保持一致；重新使用同一 npm 发布包作为基线，并对固定源码的独立副本增加预算参数传递。原始库源码与基线证据保持不变。

### 改动与条件

第一组改动只开放编译器步数和请求期限：TypeScript 请求计时、Worker 参数及 Rust 编译器会话采用同一配置，去除 Rust 内部不可调整的 30 秒截断。随后，因两项均出现 `allocation_limit`，追加开放编译器逻辑堆和对象上限。共修改五个库文件，补丁与两份实际 SDK 构建分别保留；这是实验构建，不是 npm 发布包已有的新接口。

两份构建都复用原发布包的同一编译器镜像，其压缩字节与哈希完全相同。编译算法、输入源码、请求／响应字节限制及生成界面的执行额度保持不变。构建使用 Rust 1.98.1、wasm-bindgen 0.2.128、TypeScript 5.9.3，Cargo `--locked`、release 和默认 RPC feature；WASM 标准库由固定本机 Rust 工具链构建。浏览器、Angular 外壳和 Go 工具链沿用基线。

完整工作区使用的是增加宿主 Compile 方法之前的 MRPC 声明，因此按该原始声明生成匹配的 Go Provider 和独立 TypeScript 客户端；生成的 Mini-Go 文件与原失败工作区完全一致。服务只增加可指定 SDK 目录的静态文件入口，不改业务规则。

每项使用新浏览器和编译器会话，串行运行，依次要求 `open → analyze → prepare → 浏览器执行 → 实际按钮提交 Go MRPC`。在首个失败处结束，不把没有到达的阶段算作通过。表中时间为整项观察耗时，包含创建、传输及停止收尾，故可略高于单请求期限。

| 条件 | 步数 | 单请求期限 | 逻辑堆／对象上限 | 完整工作区 | 精简工作区 |
| --- | --- | --- | --- | --- | --- |
| 原发布包默认 | 1 亿 | 30 秒 | 128 MiB／50 万 | 步数超限；open；25.95 秒 | 期限超限；open；32.91 秒 |
| 重建版默认 | 1 亿 | 30 秒 | 128 MiB／50 万 | 步数超限；open；22.94 秒 | 步数超限；open；31.81 秒 |
| 仅增加步数 | 10 亿 | 30 秒 | 128 MiB／50 万 | 期限超限；open；34.02 秒 | 期限超限；open；34.00 秒 |
| 仅延长期限 | 1 亿 | 120 秒 | 128 MiB／50 万 | 步数超限；open；23.14 秒 | 步数超限；open；31.69 秒 |
| 步数与期限同时增加 | 10 亿 | 120 秒 | 128 MiB／50 万 | 分配超限；open；50.05 秒 | 分配超限；open；45.75 秒 |
| 再增加堆／对象额度 | 10 亿 | 120 秒 | 512 MiB／200 万 | 期限超限；open；123.96 秒 | 期限超限；open；123.86 秒 |
| 关闭步数限制并延长到 300 秒 | 不限累计步数 | 300 秒 | 512 MiB／200 万 | 期限超限；open；303.92 秒 | 期限超限；open；303.99 秒 |

共 7 个条件、每条件两份输入，**14 项均在 `open` 失败**。没有进入后续独立 `analyze`、`prepare`、生成镜像执行或 RPC 检查，不将未到达阶段计为通过。每条件只运行一次；这组对照用于识别限制，不能作为稳定时延或性能排名。

重建默认配置的精简工作区先触发步数上限，原发布包先触发期限；两者都在约 30 秒附近停止。它们的 WASM 构建环境不同，哪一项先触发会随执行速度变化，不能用错误名称变化推断功能已改善。主要因果比较使用同一实验构建中的不同额度。

### 解释与采用边界

默认步数和期限确实会截断处理；只增加步数会遇到时间限制，只延长期限仍会遇到步数限制。两者同时放宽后出现分配超限，说明原问题还涉及编译器的内存／对象预算，不能简化为一个默认值过小。`allocation_limit` 将对象数与逻辑字节检查合并，本实验没有分别测量哪一项先达到上限，不把该错误直接写成整个浏览器内存耗尽。

扩大堆／对象额度后，两份工作区都在 120 秒期限处停止；进一步关闭累计步数限制、延长到 300 秒，仍未完成打开。因此，本次条件不足以证明“放大或解除默认 limit 即可解决”。关闭的是累计步数限制，时间、内存、请求大小与主动取消仍保留；没有运行时间和内存均无限的条件，也不推断继续扩额必然成功或永远不能成功。

采用边界保持明确：正常界面使用匹配的宿主编译镜像，浏览器编译按已验证范围开放。预算可配置可作为库改进方向，但实验参数不是推荐默认值，更不是已发布修复。原主链路 14 项通过、原生编译的桥接补充四项通过不受本对照影响。

`open` 会建立语言引擎并执行初始分析，并非仅登记文本。失败发生在该阶段，不能据此认定后续生成、运行或 RPC 契约不支持，也不能以原生 Go 编译同类源码成功替代此路径通过。单凭预算对照不能定位实际开销；进一步的依赖和采样诊断见[慢编译诊断](#compiler-diagnosis)，其中仍不将 GC 热点等同于内存泄漏。

### 取消与恢复

在关闭累计步数限制、300 秒期限及 512 MiB／200 万对象条件下，另行检查控制能力：对原精简工作区的 `open` 在开始约 200 ms 后安排取消，请求从开始到返回 `AbortError` 为 2,201.5 ms；页面主线程期间推进了 220 次定时回调。随后在**同一个语言服务对象**中打开、分析、编译并执行小型纯逻辑工作区，返回预期文本，耗时约 5.94 秒；结束时编译器的活动 scope、task 和 FFI 计数为零。

该检查通过，但不表示取消即时完成。SDK 原有的两秒强制停止兜底保留，本次记录未单独区分协作取消与强制终止路径；服务对象复用也不表示底层 Worker 或失败工作区现场得到保留。此结果证明主动停止与小型工作区重新使用可行，不证明大工作区可完整编译或恢复。

<a id="compiler-diagnosis"></a>

## 慢编译诊断与使用方式核对

**未发现原实验的 API 使用错误；实际瓶颈涉及标准库依赖展开，以及在 VM 中运行编译器的执行、GC 和计时开销。** 此结论来自同源原生对照、空白浏览器页面、依赖图、CPU 采样与 Mini-Go 调用栈，不能简化为默认预算过小，也不表示任意源码的浏览器编译都不可用。

### 调用契约

固定版本的[官方示例](https://github.com/d7z-team/mini-go/blob/ae1bcd63796d5bfc93da8e93c4baedcd9d49779a/playground/runtime-rust/runtime-wasm/README.md)同样使用 `createLanguageService → open → analyze`。本实验的 Root、Namespace、ModulePath 和文件输入与契约一致，编译器镜像与 SDK 匹配；语言服务内部已经使用 compiler 额度，不需要调用方额外传入普通 VM 的 `workload` 选项。

`open` 通过 [service.New](https://github.com/d7z-team/mini-go/blob/ae1bcd63796d5bfc93da8e93c4baedcd9d49779a/compiler/service/session.go)建立初始分析快照；同一修订再次 `analyze` 会复用已分析结果。原失败没有执行到后续 `analyze`，因而不可能由这次后续调用造成。`Editable` 只约束编辑权限，不会让编译器跳过只读依赖的类型检查。

另按上游[直接编译示例](https://github.com/d7z-team/mini-go/blob/ae1bcd63796d5bfc93da8e93c4baedcd9d49779a/playground/runtime-rust/runtime-wasm/tests/compiler_scenario.js)，用原发布包指定 `workload: "compiler"`，直接发送 `Operation: "check"`：纯函数约 260 ms 完成，原精简界面在 75 秒观察窗内仍未完成。该对照只检查编译前端，不等于完整 `prepare`；结果不支持“换一个入口即可快速完成”，也不否认语言服务还承担额外的索引与文档工作。

### 依赖放大与独立页面对照

精简界面自身只有 639 字节，却通过 `ffi → errors → reflect → strconv` 引入数学、Unicode 等依赖。[ffi](https://github.com/d7z-team/mini-go/blob/ae1bcd63796d5bfc93da8e93c4baedcd9d49779a/stdlib/src/ffi/ffi.mgo)使用 errors，[errors](https://github.com/d7z-team/mini-go/blob/ae1bcd63796d5bfc93da8e93c4baedcd9d49779a/stdlib/src/errors/errors.mgo)使用 reflect；依赖图由同版本库的 `LoadHeaders` 实际生成，而非按 import 文本估算。

空白页面只加载 SDK，没有 Angular、绘制桥或业务 RPC。语言服务使用前述扩额构建、不限累计步数、512 MiB／200 万对象及 120 秒请求期限；每秒低频记录 VM 统计。CDP 以 1 ms 间隔采样，各例独立、串行运行。原生对照执行相同输入的 `ToolService.Execute(workspace/open)`，不是用单个裸函数的编译耗时替代整个工作区。

### CPU 与客体调用栈

原精简界面前 30 秒约 97.7% 的采样时间处于 VM `poll_loop` 调用栈中，主要计算已经发生在 Worker 内。该区间计时相关调用栈约占 25.5%，GC 调用栈约占 8.7%；30～60 秒 GC 栈约占 43.2%；60～80 秒计时栈约占 29.7%、GC 栈约占 9.8%。这些是包含子调用的栈采样占比，不能相加，也不能直接当作优化后的加速比例。

源码中，[执行循环](https://github.com/d7z-team/mini-go/blob/ae1bcd63796d5bfc93da8e93c4baedcd9d49779a/playground/runtime-rust/src/instance.rs)逐步推进指令并检查定时器；[定时器处理](https://github.com/d7z-team/mini-go/blob/ae1bcd63796d5bfc93da8e93c4baedcd9d49779a/playground/runtime-rust/src/instance/timer.rs)在存在定时器时读取时钟；语言工具的请求上下文会建立截止时间。这解释了有实际功能作用的计时开销，不能通过删除取消和期限保障来宣称性能改进。GC 采样主要落在对象追踪及根扫描；高占比不等于已经证明泄漏。

原发布包的直接 check 另在暂停后读取客体栈。约 10、20、30、40 秒依次观察到 `semantic.analyzeExpr`、`parser.parseExpression`／`source.Span.Valid`、`scanner.position` 及 `ast.assignExpressionIDs`。这证明被观察的慢路径确实在扫描、解析、构造语法结构和语义分析，而非等待业务 RPC。有限采样不证明所有路径均可结束，也没有得到各标准库包的精确总耗时占比。

### 采用与优化方向

正常展示继续复用匹配镜像，源码编辑可使用宿主编译。需要浏览器语言工具时，复用会话，通过 `update/analyze` 处理编辑；反复新建会话或重新 `open` 会扩大冷启动成本，但不是原实验首次 `open` 失败的原因。编译器镜像内携带标准库源码，不等于已为当前工作区准备好了可直接复用的分析结果。

库侧值得按顺序评估：缩小基础 FFI 的传递依赖；在保持源码、目标和编译器身份匹配的前提下复用标准库分析；依据采样优化 GC 追踪及定时器检查频率。直接编译入口可减少不需要的语言服务工作，但本次未证明足以解决整个问题。以上是有证据支持的优化方向，尚未作为修复实施或取得优化后的端到端成绩，不将调大额度当作完成修复。

诊断材料保存原生结果、完整依赖图、输入消融、CPU profile、VM 统计、暂停调用栈及脚本。首次栈探针未暂停 VM，得到 `not_paused`；修正为暂停后读取，取得四组有效栈，原错误保留。被中断的运行与本机端口权限错误不计作编译功能失败。原基线及预算实验冻结材料均校验未变。诊断包 109 项材料的 SHA-256 清单为 `a5ab471c56032d2d1f043ae84e7b2119d5b6c097705a1c2a7841b2ebcff88962`。
