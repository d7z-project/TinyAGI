## result-revalidation

原分析截至 2026-09-20；以下为形成时的研究材料，现行方案见总设计与当前专题。

<a id="result-revalidation-three-questions"></a>

### 1. 分开处理三个问题

慢速模型在旧上下文下产生结果，需要分别判断：

1. 结果包含的事实、分析或证据是否仍有保留价值。
2. 当时选择某个方案的理由是否仍然成立。
3. 对应动作在执行时是否仍被允许、仍满足能力契约。

这三者不等价。某资源仍然可用，不代表它仍是最新目标下的最佳选择；用户取消一次动作，也不必让已经得到的研究材料消失。结果的保留与访问仍受授权、删除和保留期规则约束。

因此候选方向是：先按 Operation 完成事实接收合法结果，再分别复核其结论和动作意图。旧动作不获准派发时，可以保留可访问的分析供新步骤使用；不能自动把原结果作为新一轮行动授权。

这不改变“状态变化与已接纳请求共同提交”的候选原子边界。被拒绝动作所依据的模型响应，通常已经是独立的完成事件，而不是必须随动作一起删除的数据。


<a id="result-revalidation-dependencies"></a>

### 2. 两类依赖

**推理依据**记录认知实际使用的事实、证据、比较范围、目标版本和重要假设。它们改变时，宿主可以指出变化，但通常不能自行断言原结论仍然正确。

**执行条件**记录能力要求的身份、参数范围、授权、资源状态和时效。条件具备明确判定方式时由宿主或提供者强制校验，不能由模型省略。

例如“选择候选 A，因为查询范围内 A 的成本最低”依赖一个候选集合。新增更便宜的候选 B 后，A 的对象版本可以完全不变，执行 A 也仍可能合法，但原来的比较结论已经需要复核。只检查 A 是否可用不足以保留“最优”这一结论。


<a id="result-revalidation-dependency-set"></a>

### 3. 依赖清单的候选组成

| 类型 | 需要表达的信息 | 只记录对象版本会遗漏什么 |
| --- | --- | --- |
| 对象读取 | 标识、所属空间、版本、实例代号或创建身份 | 删除后用相同 ID 和局部版本重建 |
| 查询集合 | 查询条件、范围、可见范围、读取快照与集合变化依据 | 新增、移除或不再符合条件的成员 |
| 否定判断 | “没有冲突”“未找到证据”对应的查询及覆盖范围 | 把空结果误当成没有依赖 |
| 时间条件 | 截止时间、观测有效期、时钟依据 | 没有状态写入时也会过期 |
| 交互与目标 | 用户轮次、目标版本、取消与取代关系 | 旧任务结果被错误用于新指令 |
| 权限 | 授权主体、范围、代号、失效条件 | 撤销后重新授权不必允许旧请求继续 |
| 提供者身份 | 服务实例、绑定代号、契约版本 | 新服务不能自动接受旧句柄或旧假设 |

全局世界版本仍可用作历史定位或保守回退，但不能独自表达以上语义。对象版本更细，也不等于依赖完整。

交互轮次约束按活动声明的范围适用：新消息不必取消所有已授权的后台研究。当前资源占用实验刻意选择绑定原交互与授权代号的请求；不能把该条件直接推广成“任何新对话都使全部长期任务失效”。

“查询集合版本”是待研究的抽象，不要求每个查询都新增数据库计数器。可能的实现包括范围版本、索引快照、可串行化查询或资源所有者提供的专用令牌。它们的开销、覆盖范围和过度拒绝程度需要比较。

再次读取一个滞后索引，或仅比较上次结果列表的哈希，不能自动发现尚未进入该索引的新成员。新鲜性依据必须来自拥有相关状态的服务，且覆盖实际查询范围。


<a id="result-revalidation-capture"></a>

### 4. 依赖如何产生

宿主可以记录实际读取到的对象、检索范围、权限和时间信息。模型可以补充关键假设及证据关联，但不能把模型声明的清单直接视为完整证明。

实际读取也不等于有效推理依赖：模型可能读取但没有使用某项信息，也可能基于常识、隐含比较或缺失证据形成判断。将全部输入一律作为强依赖会保守拒绝很多结果；只相信模型挑出的依赖又可能遗漏条件。

待比较的候选包括：保守保存全部读取范围、模型声明加宿主读取审计、能力契约提供必要执行条件。E2 当前实验只比较了清单已知时的校验行为，尚未验证这些清单如何自动生成。


<a id="result-revalidation-revalidate"></a>

### 5. 变化后的处理

| 观察 | 候选处理 |
| --- | --- |
| 所有必要依赖仍有效 | 按现有授权继续，并记录复核时点 |
| 对象版本变化，但明确的执行条件仍满足 | 可通过该执行条件检查；是否保留原决策还需检查推理依据 |
| 推理依据或目标变化 | 将变化与原结果交回认知层，允许局部修订、补充证据或重新思考 |
| 授权撤销、轮次过期或资源已替换 | 拒绝原动作，不能通过自动重试恢复旧授权 |
| 无法判断数据新鲜性或覆盖范围 | 保留未确认状态，补充查询或等待；不伪装成依赖未变 |

对“局部修订”的研究重点是：是否能复用没有失效的工作，以及如何避免被旧结论锚定。不能简单把新字段覆盖进旧上下文，就认为完成了重新推理。

完整条件校验在合成资源任务中有效，只说明已知条件足够时可以减少不必要拒绝；它不应被扩展成大量固定领域规则。关注什么、如何比较方案及是否值得继续思考仍属于开放认知。


<a id="result-revalidation-execution-window"></a>

### 6. 提交与执行之间仍有窗口

宿主通过校验以后，世界仍可能在文件、工具、设备或外部 API 执行前变化。需要按能力契约区分保证：

- 同一权威状态内，条件校验与写入可以共同提交，并维护必要的唯一性或排他约束。
- 提供者支持条件执行时，将它能够验证的身份、版本、范围和有效期传给它，不能只在调用前检查一次。
- 提供者只支持目标对象条件写时，不能由此推出跨对象集合、授权或交互条件也受到保护。
- 条件跨服务或依赖物理世界时，不默认存在共同原子边界。需要明确授权时效、取消确认、结果核对或本地控制器保证的范围。

“用户提出取消”和“远端确认不会执行”分别记录。对于无法即时撤回的远端操作，界面与认知状态不能声称已经停止；本地语音播放的直接停止通路仍可独立工作。


<a id="result-revalidation-evidence"></a>

### 7. 证据与开放问题

[E2 实验](../experiments/003-result-revalidation.md)支持将对象身份、集合读取、授权代号和时间条件加入依赖研究，并说明串行提交本身不足以弥补遗漏的依赖。

现有证据没有证明某种校验策略全面更优，也没有决定心智调度必须串行或并行。待验证：模型能否表达关键推理依据、宿主读取记录能补足多少遗漏、局部修订是否比完整重算更划算，以及提供者实际能承诺哪些条件执行语义。

## recovery-decisions

原分析截至 2026-09-20；以下为形成时的研究材料，现行方案见总设计与当前专题。

<a id="recovery-decisions-decisions"></a>

### 1. 当前决策

| 问题 | 采用方案 | 理由与边界 |
| --- | --- | --- |
| 谁保存事实 | 一个宿主中的 SQLite＋本地文件 | 不再保留独立 authority／provider／world 数据库部署；它们曾是实验夹具 |
| 谁运行待办 | 同一进程中的派发器 | 数据库保存责任，内存通知只唤醒，扫描负责恢复 |
| 如何防重复启动宿主 | 稳定锁文件上的操作系统独占锁 | S1a 删除锁对象会造成双持锁；正常启停不 unlink，不传递锁描述符给工具 |
| 如何承认接纳 | 意图及待办事务提交后返回 | 避免确认成功但重启找不到工作 |
| 如何处理结果不明 | 原键查询、按契约重试或保留 unknown | SQLite 不能替外部效果提供原子性 |
| 如何取消 | 未进入则事务关闭；已进入则请求停止并核对 | 取消请求不是已停止证明 |
| 如何恢复备份 | 关闭派发、核对快照与外部缺口后按范围恢复 | 更换运行身份不允许重放历史动作 |


<a id="recovery-decisions-entry"></a>

### 2. 本地接纳与执行进入

宿主先提交 Operation 和待办，再确认接纳；派发前记录尝试与业务键。工作者在同一个 SQLite 事务边界检查状态并将 queued 改为 entered，只有成功者可以调用能力。进入和实际效果之间仍没有共同事务。

重启扫描未进入的待办可以继续；已进入且结果不明的非幂等动作不能自动回 queued。entered 既可能对应效果尚未发生，也可能对应效果发生后未保存回执。E8d 的这项反例在单机仍成立，保留原键和核对责任即可，不再沿用节点启动代号。

第三方模型或工具服务是否持久接纳、去重和保留查询结果，由其自身契约决定。TinyAGI 的本地接纳不是第三方接纳成功。


<a id="recovery-decisions-cancellation"></a>

#### 2.1 取消与进入的裁决

queued → closed 和 queued → entered 在 SQLite 中条件转换，不能先检查内存缓存后无条件执行。关闭提交后才确认不会由此本地入口启动；entered 的工作只能先请求取消，再根据实际能力核对。

本机停止播放可以直接由原生控制路径执行，随后持久登记事实。外部请求、第三方子进程和设备另有停止语义；关闭 VM 或取消等待不替代这些证明。所有执行入口是否都遵守规则，仍需在本地闭环中验证。


<a id="recovery-decisions-restore"></a>

### 3. 正常重启与旧备份恢复

正常重启：取得同一锁对象上的独占锁，检查存储，生成新 RunID，恢复最后确认的认知部署；已完成提交按原键返回，未派发意图继续，未明外部动作核对。新 RunID 仅标识本次执行，不代表外部工作消失。

恢复旧备份另按以下顺序：

1. 停止旧宿主，确保其不能继续派发；如存在被能力启动的子进程，单独核对其退出，不能仅以宿主退出推断。
2. 动作派发保持关闭，在独立恢复目录校验数据库、文件清单和代码版本，完整后才使用该目录。
3. 记录备份时间和已知缺失区间，检查未完操作及快照之后可能发生的请求。尽量使用外部可查询记录补充；没有证据时明确保留信息缺口。
4. 对结果不明或原键保留已过期的动作停止自动重放。已独立核对权限、容量和冲突的新工作可以按范围继续。
5. 核对结果、限制和恢复决定入库后开放相应功能，不能因为 SQLite 可连接就宣布全部恢复。

E8e 表明回退状态后自增旧计数或换身份直接重发均可能重复效果；它没有证明完整灾备。单机不需要跨节点恢复代号和接管屏障，但需要确认旧进程退出、处理遗留工具和恢复后的外部信息缺口。


<a id="recovery-decisions-settlement"></a>

### 4. 停止证据与必要资源账务

纯内存临时资源由进程内生命周期管理；需要跨重启保留的费用和冲突责任才有持久预留。证据绑定来源、操作、尝试、具体资源与 ReservationID，不按资源显示名释放新占用。

结算在一个 SQLite 事务内核对预留状态与证据，将释放状态、余额返还、按 ReservationID 唯一的释放记录及必要事件共同提交。E8d 的分离提交会重复返还；多个 ProofID 也可能只是同一预留的多份证明。

效果与停止分别判断。确认本地计算已退出可释放该计算的容量，外部效果仍可 unknown；不能将未知效果扩大成冻结所有本地工作，也不能用本地退出证明远端工作停止。


<a id="recovery-decisions-conflicts"></a>

#### 4.1 矛盾证据

同 source＋ProofID 的相同内容视为重送，不同内容保留并标记冲突。结算事务重新读取冲突状态，不以事务外缓存决定返还。已释放后才出现矛盾时保留原账，暂停受影响的新分配并追加核对，修正需新证据。

E8e 只验证给定来源下的内容冲突，不解决不同来源谁真实、资源已再次使用后怎么办或何时可以解封。这些机制只在具体能力需要时验证，不为每个纯计算任务建立完整证明系统。


<a id="recovery-decisions-backend"></a>

### 5. SQLite 和本地文件

数据库产品已确定为 SQLite，不再安排 PostgreSQL、复制主备或消息代理选型。S1a 已使用 WAL／FULL；采用上下文读取结束后再以 BEGIN IMMEDIATE 开始短写事务，BUSY_SNAPSHOT 回滚重读。单写入通路容量、索引及 checkpoint 参数保留为尚未测量的工程项。

业务状态、待办、必要预算和回执放入同一个数据库；大文件先完成本地发布，再提交引用。备份包含数据库快照和全部必要引用文件，维护入口关闭新准入，排空完整文件发布及引用事务，再协调备份／删除／回收；回收还排空相关读者。完成标记不能替代数据库与文件清单复核。完整协议、一手资料和未定参数见[存储专题](../runtime-protocol.md)。

### 6. 保留的工程验收范围

下表不是当前推进队列。已有约束继续适用，剩余机制验证暂缓，研究优先处理完整活动与任务效果。

| 要求 | 验证场景 |
| --- | --- |
| 单目录只运行一个宿主 | 双启动、崩溃遗留锁文件、退出未完成；确认第二实例不派发 |

| 不盲重放外部动作 | 调用前后崩溃、回执缺失、键过期与旧备份 |

### 7. 证据入口及限制

## storage-options

原分析截至 2026-09-20；以下为形成时的研究材料，现行方案见总设计与当前专题。

<a id="storage-options-decision"></a>

### 1. 为什么这样选

一个进程内已有宿主调度与状态所有者，SQLite 提供本地关系查询、唯一约束和原子提交；普通文件保存媒体与大内容。这样无需运营额外数据库或存储服务，也无需自行实现对象 HEAD、日志索引和跨节点提交协议。

选择来自用户约束与复杂度评估。E8b～E8e 使用 SQLite 验证过部分真实进程和事务窗口，支持继续研究本地提交；它们没有证明产品容量、文件耐久性、磁盘故障恢复或数据库排名。[S1a](../experiments/010-local-storage.md)随后补充了文件发布、备份、回收和锁对象的真实本地反例，仍未测试掉电或完整产品。单二进制也不意味着所有数据只能存一个文件。


<a id="storage-options-data"></a>

### 2. 数据职责

| 数据 | 保存方式 | 约束 |
| --- | --- | --- |
| Self、Mind、Goal、活动、连续状态、断言 | SQLite | 版本、来源、访问范围与关联查询 |
| 事件、Operation、Effect、待办、提交回执 | 同一个 SQLite 数据库 | 同一意图需要的状态和待办共同提交 |
| 必要预算、预留与结算 | 同一个 SQLite 数据库 | 唯一结算，费用未知时不冒充已结清 |
| 原始媒体、大证据、源码产物、导出 | 本地不可变文件为主 | 数据库登记逻辑 ID、相对路径、长度、摘要和可见范围 |
| 小文本、摘要、结构化记忆 | SQLite | 不强制所有内容外置，也不预先固定大小阈值 |
| 精确、时间、实体查询 | SQLite 索引 | 首个检索基线 |
| 全文检索 | 优先评估 SQLite FTS5 | 验证中文分词、更新／删除和权限过滤 |
| 可选向量索引、资源读取／计算结果缓存 | 本地可重建派生数据 | 显式读取或计算产生，记录来源版本，不是唯一事实源 |
| 模型 KV／前缀缓存 | 推理组件管理；宿主仅保存清单及支持的句柄 | 不要求导出到 TinyAGI 本地目录，不假定跨组件兼容 |
| 沙箱配置、活动状态与试验报告 | 同一 SQLite 分域记录，产物用本地文件 | 宿主绑定 SandboxID；只读基准与独立写入分开，模拟事实不进入现实记忆 |

文件在认知中默认只有[资源投影](../projection-input-and-compute.md#projection)，主动读取后才带入正文／派生内容；存储里保存了摘要或缓存不等于本轮模型已选择读取。新建全文或向量索引也是有范围的读取任务，不在资源登记时默认执行。

本地文件不是权限绕过路径。宿主通过逻辑引用查权限，再解析受控目录中的文件；不把模型给出的任意路径直接视为授权。内容摘要用于校验，不等于来源认证。不同访问范围的物理去重先不作为必要功能。


<a id="storage-options-layout"></a>

### 3. 目录与运行边界

```text
tinyagi                       单个可执行文件
<data-dir>/
  state.sqlite                唯一业务数据库，WAL／SHM 由 SQLite 管理
  files/                      媒体、证据等已发布内容
  artifacts/                  认知源码、构建输入、验证结果
  sandboxes/<id>/              各试验独立产物与材料，元数据仍在 state.sqlite
  tmp/                        同文件系统的未发布内容
  cache/                      可清空的派生缓存
  logs/                       有界运行日志，不代替业务记录
  runtime.lock                操作系统锁的载体
<backup-dir>/                 独立备份目录与完成清单
```

这是逻辑布局候选，目录名不是接口冻结。宿主持有数据目录独占锁直至完全退出；第二个宿主不得同时使用该目录。锁文件存在不代表锁仍被持有，PID 检查也不替代实际进程锁。数据库位于本地文件系统，不通过网络共享给其他机器。

沙箱目录不是单独的安全证明；候选通过宿主限定的逻辑资源入口读写，不获得整个数据目录或数据库连接。试验记录、报告和可导出产物按原隐私及保留范围管理，目录清理不得破坏仍被采用报告引用的材料。当前只补充这些数据职责，具体生命周期随[沙箱完整任务验证](../sandbox-evaluation.md#validation)明确。

Linux 基线采用稳定路径上的非阻塞独占 flock。S1a L1 表明崩溃后的同一锁对象可以重新取得，L2 表明删除重建路径会让新旧进程分别持有锁，因此正常启停不 unlink 锁文件。锁描述符不传入工具子进程；这是基于内核契约的要求，继承树尚未实测。advisory lock 约束合作宿主，不是防止任意进程修改数据的访问控制。[Linux flock](https://man7.org/linux/man-pages/man2/flock.2.html)

SQLite 库嵌入进程。Go 驱动需验证单文件发布、目标系统兼容性、SQLite 版本和所需扩展；当前不预先选择 CGO 或纯 Go 路线，也不因此引入数据库守护进程。显卡驱动和可选能力的模型权重属于环境资源。


<a id="storage-options-transactions"></a>

### 4. 数据库事务基线

宿主采用一个写入通路，短事务处理状态、意图、必要预留、输入消费及回执；多个心智可并行计算。固定读取上下文后结束读事务，再调用模型，提交时重新核对可变条件。不持有事务等待外部调用或文件生成。

采用 WAL＋`synchronous=FULL` 作为当前持久化基线，计算完成后使用 `BEGIN IMMEDIATE` 开始短写事务并复核条件；检查实际启用结果与每条连接的配置。S1a 已观察该事务的互斥与后续合法进展。读连接数、忙等待、checkpoint 周期和批量大小由负载决定，不能靠无限重试掩盖事务过长。初始基线禁止关闭同步以制造更好性能数据。

S1a T1 的旧读快照升级返回 `SQLITE_BUSY_SNAPSHOT`，回滚并重新读取后才可写；此类错误不靠延长 busy 等待解决。T3 的长读事务阻止 checkpoint 完全推进，因此模型调用、长检索处理与文件等待前结束读事务。普通 `SQLITE_BUSY` 按事务阶段有界处理，确认事务状态后复核重试；提交结果不明时查询原业务键。实验的 busy=0、关闭自动 checkpoint 只为暴露现象，未据此选定产品参数。[SQLite isolation](https://www.sqlite.org/isolation.html)、[事务文档](https://www.sqlite.org/lang_transaction.html)

重要待办保存在库中，内存队列负责唤醒；启动和周期扫描恢复遗漏唤醒。相同提交或操作的稳定键有唯一约束。通知不是事实源，外部工具调用不参与 SQLite 事务。无需额外 broker，也不按模块拆分多个数据库。


<a id="storage-options-file-commit"></a>

### 5. 文件发布与业务提交

SQLite 事务无法同时原子提交普通文件。对需要持久引用的新内容，设计以下顺序：

1. 在同一文件系统的临时目录写入，计算摘要和长度，限制空间与路径范围。
2. 完成文件同步，再发布到不可变的最终位置；不覆盖已发布内容。采用内容 ID 或唯一 ID，遇到已有文件必须核对内容。
3. 按目标操作系统和文件系统的契约同步相关目录元数据；只有完成所要求的持久化步骤，才允许提交引用。跨目录发布涉及的目录均需处理。
4. 在 SQLite 事务中保存文件记录、引用及关联业务状态，再返回成功。
5. 提交失败或进程崩溃可能留下未引用文件，之后按清理规则回收；不得因临时文件存在就认为业务提交成功。

| 中断点 | 恢复解释 |
| --- | --- |
| 临时文件未完成 | 无正式引用，可清理残留 |
| 文件已发布，数据库未提交 | 孤立文件，不是已生效业务数据 |
| SQLite 提交完成，返回前崩溃 | 查询原提交键并返回已存回执，不重建新意图 |
| 已提交引用对应文件缺失／摘要不符 | 数据损坏或不完整恢复，阻止依赖动作并报告，不能默认为空文件 |

S1a F1～F6 支持上述顺序在指定进程终止点的恢复，并验证原请求可以继续完成；F7 的相反顺序产生悬空引用。该结果只覆盖小型夹具。Linux 上文件 `fsync` 不自动同步目录项；其他系统须按其契约验证，不能仅凭 rename 成功声称掉电耐久。文件可见性、SQLite 提交与真实磁盘持久性分别验证。[Linux fsync 文档](https://man7.org/linux/man-pages/man2/fsync.2.html)

数据目录、文件子目录或备份目录新建时，还需按目标文件系统处理目录创建及父目录的持久化；S1a 未覆盖这条初始化掉电链路。任何失败都不能确认成功。

外部用户文件的修改属于 Effect，不等同内部不可变文件发布；它仍有取消、覆盖和崩溃结果不明的问题，须按具体工具契约处理。


<a id="storage-options-backup"></a>

### 6. 备份、删除与回收


<a id="storage-options-maintenance"></a>

**统一维护入口：停止新准入 → 排空已有发布／读取 → 维护 → 恢复准入。** 发布资格必须覆盖文件准备、发布、引用事务直到成功或明确放弃。清理、删除与备份不能绕过入口；维护超时不得直接跳过排空，后续研究有界退回或延迟维护，不将实验中的等待上限当产品参数。S1a G1 误删在途文件，G2/G3 的受控线程排空保留了有效引用和读者。

首次备份方案先追求可验证：停止接纳新的数据修改，等待已开始的文件发布及其引用事务完成或明确放弃，再暂停写入、删除和回收；使用 SQLite backup API 生成一致数据库副本，再复制该副本引用的不可变文件。校验数据库、文件与版本清单，完成后发布备份完成清单并恢复写入。恢复时重新核对数据库格式／完整性、数据库摘要、引用集合及各文件长度／摘要，不只检查标记存在；S1a B4 的不完整副本即使有伪造完成标记也被拒绝。允许输入有界缓冲，超限明确拒收；不必等待所有外部工作结束，其恢复责任写入快照。

不能将运行时随手复制的 `.db` 视为完整备份，未 checkpoint 的已提交状态可能仍在 WAL；也不能恢复数据库后从当前目录随意补不同版本文件。备份期间外部效果仍可能发生，恢复后必须核对。S1a B1 的原始 db 副本漏掉 WAL 提交，B2 的数据库快照因后续回收缺失文件，B3 的受控完整副本可恢复；备份暂停耗时、失败清理和存储空间仍纳入后续 S1。

首个回收方案使用同一维护入口，停止接纳新写入、发布和文件读取，等待在途发布及其引用事务完成或明确放弃、相关读者退出，再从 SQLite 引用集合确定候选孤立文件。不能将“已发布但引用事务仍在等待”的文件当孤立文件删除。备份复制与回收互斥，已完成备份包含自己的文件副本。暂不引入在线并发 GC。删除已引用内容时先提交删除／撤销访问状态，使索引和缓存失效，再处理物理文件；处理中崩溃只能留下不可访问的残留，不能恢复旧授权。

历史备份可能仍包含已删除内容，保留期限及备份删除需明确管理，不能宣称在线删除已抹去全部副本。数据目录损坏时的恢复能力取决于可用备份，当前没有自动复制或高可用保证。


<a id="storage-options-alternatives"></a>

### 7. 已移除的方案

| 替代项 | 不采用的理由 |
| --- | --- |
| PostgreSQL 等独立数据库服务 | 超出单进程嵌入式存储要求，当前没有需要额外服务的实测负载 |
| 对象存储主后端及 HEAD 条件提交 | 文件已明确本地化；自行维护提交链、索引和回收增加协议负担 |
| 纯文件／JSON 承担全部业务状态 | 需要自建关联更新、去重、查询和恢复机制，SQLite 更直接 |
| 每个模块一个 SQLite 库 | 必要共同提交的边界被拆开，历史多库实验仅用于暴露该问题 |
| 消息代理、独立全文／向量服务 | 内存唤醒、SQLite 待办和本地索引先作为基线 |
| 所有文件都存 SQLite BLOB | 不作为默认，大媒体可能延长事务并放大备份；小内容是否内联按负载测量 |

这些决定遵循当前范围，没有将未测方案写成性能落败。容量、成本和查询质量仍需验证。

### 9. 尚未验证的部分

S1a 已完成指定文件发布切点、备份闭包反例、受控维护线程、锁对象和 SQLite 快照／写锁测试。注入的 EIO／ENOSPC 仅证明该夹具错误路径没有确认业务成功，不是实际坏盘或磁盘满验证。

未测范围包括真实工作负载、Go 驱动及构建依赖、容量、维护等待与饥饿、路径解析、删除与保留期、损坏恢复及旧备份之后的外部信息缺口。它们作为[支撑研究记录](../research-plan.md#s1)保留，当前不逐项补齐，也不作为整体研究前提。完整认知活动的推进见 [C1](../research-plan.md#whole-system)；其任务质量不能由本专题的机制结果代替。
